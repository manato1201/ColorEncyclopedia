# 第 0 回 全体の見取り図

> 所要時間の目安: 1 時間 / 前提: HTML・TypeScript の基本

## この回のゴール

- Markdown(frontmatter つき)が、**ページと可視化になるまで**の流れを説明できる。
- 計算を**純粋関数**に分けてある理由を説明できる。
- 「数値を手で書かない」方針を説明できる。

## 1. 図鑑の作り

![構成図](../diagrams/architecture.svg)

1. **コンテンツ**: `content/colors/*.md`(色)・`content/shapes/*.md`(図形)。先頭の **frontmatter**(`name`・`category`・`colorValue` など)と、本文の Markdown。
2. **ローダー**(`createContentLoader`): frontmatter と本文を読み、**一覧用の軽いメタデータ**と、**詳細用の本文 HTML** を返す。色と図形で、**同じローダーを共有**する。
3. **ページ**(Next.js の App Router): ローダーのデータと、計算(`src/lib`)と、可視化を組み合わせる。
4. **可視化**: 2D は canvas、3D は three.js(「立体」を選んだときに初めて読み込む)。
5. **検査**(`npm run verify`): コンテンツと計算が、**矛盾していない**ことを、毎回機械で確かめる。

## 2. 計算は純粋関数

色の変換(`color-math.ts`)・間隔反復(`spaced-repetition.ts`)・3D の幾何(`geometry3d/`)は、**画面にも保存先にも依存しない純粋関数**です。理由は 3 つ。

- **Node だけで動かして検査できる**(`verify`・この講義の例)。
- **画面のあちこちで、同じ結果になる**(唯一の実装)。
- 保存先(localStorage)や three.js を入れ替えても、**計算は変わらない**。

## 3. 数値を手で書かない

README にも画面にも、色の数値や収録数を**手で書かない**方針です。

| 数字 | 出どころ |
|---|---|
| HSV・Lab | 収録した **HEX から計算**(`color-math.ts`)。frontmatter の値との一致を `verify` が確認 |
| 収録数・可視化の数 | `npm run verify` の出力 |
| 試験範囲との対応表 | `npm run exam-table`(問題データから生成) |

> 手で書いた数字は、いつか**コンテンツと食い違う**。機械で作るか、機械で確かめる。

## 確認問題

1. コンテンツを、色と図形で**同じローダー**にしている利点は何ですか。
2. 計算を純粋関数にして、`verify` でも使えるのは、なぜですか。
3. 色の Lab の値を frontmatter に書いたうえで、`verify` が再計算して比べるのは、なぜですか。

## 解答

1. 読み込み・本文の HTML 化の処理を 1 か所にでき、色と図形で挙動がそろう。
2. 画面や保存先に依存しないので、Node だけで import して動かせるから。
3. 書き写しのミス(転記ミス)を、機械で見つけるため。

## まとめ

- **Markdown → ローダー → ページ → 可視化**。検査は `npm run verify`。
- 計算は純粋関数。数値は**計算するか、検査する**。
- 次の回は、色を数にする。
